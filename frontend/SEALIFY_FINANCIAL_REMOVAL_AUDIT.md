# SEALIFY FINANCIAL REMOVAL AUDIT

**Scope:** Step 3 read-only audit only.

No files were deleted or modified. No database objects, migrations, RLS policies, payment configuration, Cloudflare configuration, or deployment state were changed.

## A. Financial functionality inventory

The application currently contains a substantial financial feature set:

- user wallet creation, balance, pending balance, and total withdrawn values;
- transaction history and payout transactions;
- payout/withdrawal request flow;
- escrow creation, handover code/QR generation, inspection status, release, and seller wallet credit;
- promotion plans and promotion payment requests for boosted/featured listings;
- admin promotion payment review;
- admin finance dashboard cards for revenue, pending payouts, balances, withdrawn totals, and recent transactions;
- transaction receipt UI in messaging;
- analytics queries counting transactions and active escrow;
- finance-related notifications;
- seed/configuration values for minimum payout and payout processing hours.

The repository also contains financial concepts in documentation, FAQ, architecture diagrams, safety/escrow pages, and embedded legacy SQL. Those must be classified separately from executable functionality during implementation.

## C. Backend/API financial features

### Wallet API

`src/api/wallet.ts` defines `walletRoutes` with:

- `GET /`: authenticates the bearer token, reads the user wallet, and creates a zero wallet if absent;
- `GET /transactions`: reads the authenticated user's transactions with optional type/limit/offset filters;
- `POST /payout`: validates amount and balance, inserts a payout transaction, decreases wallet balance, increases pending balance, and creates a notification;
- `GET /payouts`: reads payout transactions for the authenticated user.

This module is a complete financial API and is a primary removal candidate, but its route registration was not found in `src/entry-server.tsx` during this audit. That makes it potentially dead/unmounted code, but it still compiles and is referenced by project architecture/documentation. Confirm deployment route wiring before deletion.

### Escrow server routes

`server/routes/api/escrow.post.ts`:

- validates the incoming Supabase bearer token;
- verifies the ad and buyer/seller relationship;
- checks for an existing escrow order;
- generates a handover code and QR URL;
- inserts an `escrow_orders` row;
- creates a seller notification;
- inserts an escrow-hold transaction against the buyer wallet.

`server/routes/api/escrow/[id]/release.post.ts`:

- validates the bearer token;
- loads an `escrow_orders` row;
- restricts release to the buyer and inspection status;
- marks the escrow released;
- inserts a seller transaction;
- marks the ad sold;
- sends a release notification pointing to `/wallet`.

These are server-only financial mutations and must be removed or disabled as a coordinated unit. Removing only the UI would leave live financial endpoints; removing only the routes would leave broken UI and analytics references.

### Other backend financial references

- `src/api/auth.ts`: creates a wallet during registration.
- `src/api/admin.ts`: counts pending promotion payments, lists promotion payments, approves/rejects them, updates promoted ad fields, and includes wallets/transactions in database backup/export data.
- `src/api/analytics.ts`: counts completed transactions and active escrow, and computes transaction aggregates.
- `src/api/listings.ts`: accepts and updates promotion plan/name/duration/start/end fields on ads.
- `server/routes/api/ads/[id].put.ts`: accepts promotion-related ad fields.
- `server/routes/api/ads.post.ts` and related routes: may create financial notifications indirectly, but listing creation itself is non-financial and must remain.

## D. Payment-provider integrations

No executable Paystack, Flutterwave, Stripe, Monnify, PayPal, Razorpay, or other payment-gateway SDK/API integration was found in the active source. The repository contains documentation references to Flutterwave/Paystack redirects, but no confirmed active provider implementation was found.

Current promotion payment behavior appears to be manual/request-based: a client creates a `promotion_payments` row containing plan, amount, payment method, and proof/details; an admin reviews and approves/rejects it. This is not evidence of an active external payment processor.

No credential values are included in this report.

## E. Environment-variable names related to finance/payment

The reviewed `.env.example` and `.env.production.example` files do not show active payment-provider variable names. They contain AI-provider configuration and general application/Supabase configuration, not confirmed Paystack/Flutterwave/Stripe/Monnify credentials.

The code references phone-provider names such as `TERMII_API_KEY`, `ARKESEL_API_KEY`, and `TWILIO_ACCOUNT_SID`; those relate to phone OTP, not wallet/payment processing, and are not part of the financial removal boundary.

Payment-related provider names mentioned in documentation are not confirmed environment integrations. Before deleting configuration, inspect the actual Cloudflare environment variable inventory separately without exposing values.

## G. Foreign keys/functions/triggers/views

The visible SQL explicitly shows `transactions.wallet_id` referencing `wallets.id` with cascade behavior in the active/embedded model. The repository also shows escrow relationships to ad/listing and buyer/seller identifiers in schema/viewer definitions.

Production inspection confirmed the relevant `escrow_orders` foreign keys. The repository migration set remains inconsistent because historical files still describe `escrow_transactions`.

No confirmed financial database view or materialized view definition was found in repository SQL. `src/api/admin.ts` and `src/api/analytics.ts` use direct queries rather than a repository-defined view.

No financial trigger was confirmed by repository search. The initial migration contains general trigger/function material, but deployed catalog verification is required before database deletion.

Indexes found include wallet-user, transaction-wallet/type/created-time, escrow ad/buyer/seller/status, and promotion-payment user/listing indexes. They should be removed only with their tables or through a reviewed database migration after application references are gone.

## H. RLS policies involving financial tables

Repository policy sources include:

- `wallets`: own SELECT plus admin `FOR ALL` in the initial migration; broader owner/admin `FOR ALL` in the performance migration; proposed explicit policies in the unapplied Phase 2B migration.
- `transactions`: own-wallet SELECT plus admin `FOR ALL` initially; owner/admin `FOR ALL` in the performance migration; proposed explicit read/admin-write policies in the unapplied migration.
- `escrow_transactions`: party SELECT, buyer INSERT, admin `FOR ALL` initially; proposed explicit party/admin policies in the unapplied migration.
- `promotion_payments`: owner SELECT/INSERT and admin `FOR ALL` initially; owner/admin broad access in follow-up/proposed sources.
- embedded/legacy SQL viewers: public `FOR ALL USING (true)` for wallets, transactions, escrow, and promotion payments.

These policies were not changed in this audit. The broad legacy policies and owner financial `FOR ALL` patterns were already identified as unsafe in the RLS audit. Financial removal must not weaken RLS or rely on deleting UI code as a security control.

## K. Promotion-payment dependency analysis

`promotion_plans` and `promotion_payments` are directly tied to paid/top-ad promotion:

1. Promotion plan rates are loaded into the application.
2. Users can submit a promotion payment request containing listing, amount, plan, payment method, and proof/details.
3. Admins review and approve/reject those requests.
4. Approval updates the ad's `featured` state and promotion name/duration/start/end dates.
5. Listing APIs accept promotion fields.
6. Admin analytics counts promotion payments and displays promotion revenue.

Therefore, removing `promotion_payments` without a decision on paid promotions would break promotion selection, approval, visibility, and admin moderation.

Clean separation options:

- If all paid promotion is removed: remove promotion UI/API/service/admin review, remove promotion fields from listing behavior, keep ordinary listing creation unchanged, and later classify `promotion_plans`/`promotion_payments` for database removal.
- If promoted listings remain but payment is external/manual: retain a non-financial promotion entitlement/status model and remove only wallet/payment collection. This requires a new product decision and authorization design.

Human confirmation is required before choosing either boundary.

## L. Recommended removal sequence

1. Confirm product scope: remove all financial features, or remove wallet/escrow only while retaining paid promotions.
2. Confirm deployed tables and actual escrow table name (`escrow_orders` versus `escrow_transactions`).
3. Inventory and preserve historical-data/retention requirements.
4. Add/adjust tests for marketplace, messaging, buyer requests, notifications, reviews, and authentication before changes.
5. Remove user-facing wallet and escrow routes/components, including shared Messages receipt dependencies.
6. Remove wallet/transaction/escrow state and queries from `SealifyContext` while preserving all unrelated context values.
7. Split financial code out of shared API/service modules; delete only the isolated financial functions after consumers are migrated.
8. Remove or redesign promotion flows according to the confirmed product decision.
9. Remove backend routes and analytics/admin queries only after route and deployment wiring is verified.
10. Search the complete repository again and run check/build plus marketplace regression tests.
11. Only after application references are gone, prepare a separate reviewed database migration. Do not drop tables in the same change as the initial frontend cleanup without catalog and retention review.

## Q. Risks and possible regressions

1. Removing wallet hydration from `SealifyContext` can break admin and user pages if consumers are not migrated together.
2. Removing escrow routes without removing links/buttons creates dead UI and potentially misleading safety claims.
3. Removing `TransactionReceiptModal` without editing Messages breaks compilation.
4. Removing wallet creation from registration may leave existing user flows or database assumptions inconsistent.
5. Removing transactions from analytics/admin backup can cause query failures if only one consumer is removed.
6. Removing promotion payments can disable featured-ad visibility and promotion moderation.
7. The active `escrow_orders`/repository `escrow_transactions` discrepancy creates a risk of deleting the wrong table or leaving live financial paths intact.
8. Broad legacy RLS policies remain a security concern; this removal must not loosen them or assume UI removal is authorization.
9. Historical financial data, legal/accounting retention, and user communication requirements are not discoverable from the codebase and require human decision.
