## 1. Overview

The Sealify API is a Laravel 12 + MySQL backend that powers the Sealify Nigeria marketplace frontend (React + Vite + TypeScript, hosted separately).

It provides:

- **User authentication** — registration, email verification (6-digit OTP), password reset, Sanctum tokens
- **Listings** — CRUD, images, search, filters, pagination
- **Categories & subcategories** — 12 parents + 48 subs seeded
- **Favorites** — saved ads per user
- **Messaging** — 1:1 conversations with text/images/files, read receipts, unread counts
- **Payments** — via PayZephyr, with 10 supported gateways (Paystack is primary, Flutterwave fallback)
- **Promotions** — free trial per user, then paid boost via Paystack checkout
- **KYC** — identity verification via Bytid sandbox/live (NIN, BVN, CAC, driver's license, voter's card)
- **Wallets & withdrawals** — balance, ledger, withdrawal requests for admin approval
- **Account status** — active / suspended / banned, with immediate token revocation

Admin endpoints (Phase 7) are being built separately with a distinct `admins` table, `admin` guard, and `/api/admin/*` routes.

## 4. Quick Start (5 minutes)

If you just want it running ASAP:

```bash
# 1. Clone
git clone <your-repo-url> sealify-backend
cd sealify-backend

# 2. Install PHP dependencies
composer install

# 3. Copy env, generate key
cp .env.example .env
php artisan key:generate

# 4. Create database (replace with your MySQL credentials)
mysql -u root -e "CREATE DATABASE sealify_backend CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"

# 5. Edit .env — set DB_DATABASE=sealify_backend, DB_USERNAME, DB_PASSWORD
#    Plus PAYSTACK_SECRET_KEY, PAYSTACK_PUBLIC_KEY, BYTID_API_KEY (see section 5)

# 6. Migrate + seed
php artisan migrate
php artisan db:seed

# 7. Create storage symlink
php artisan storage:link

# 8. Seed admin user
php artisan db:seed --class=AdminSeeder

# 9. Run
php artisan serve
```

**Test:** `curl http://127.0.0.1:8000/api/categories` → returns 12 categories.

**Docs:** `http://127.0.0.1:8000/docs/stoplight.html` → full interactive API browser.

### 5.2 Database Setup

**Create the database:**

```bash
mysql -u root -p -e "CREATE DATABASE sealify_backend CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
```

Or via phpMyAdmin: New database → `sealify_backend` → collation `utf8mb4_unicode_ci` → Create.

**Run migrations (creates all tables):**

```bash
php artisan migrate
```

**Seed initial data:**

```bash
php artisan db:seed
```

This runs:
- `CategorySeeder` — 12 parent categories + 48 subcategories
- `ListingSeeder` — 8 sample listings (owned by the first user)

**Create the initial admin (for Phase 7 admin endpoints):**

```bash
php artisan db:seed --class=AdminSeeder
```

Credentials will be printed to console:

```
Email:    admin@sealify.test
Password: admin12345
```

⚠️ **Change this password immediately** before any non-local deployment.

### 5.3 Storage Symlink

Required for images to be web-accessible:

```bash
php artisan storage:link
```

Creates `public/storage → storage/app/public`. Without this, image URLs from `/storage/...` return 404.

### 5.4 API Documentation Setup

Scramble auto-generates OpenAPI docs from your code. Confirm `config/scramble.php` has:

```php
'servers' => [
    'Local'      => 'http://127.0.0.1:8000/api',
    'Production' => 'https://api.sealify.ng/api',
],

'ui' => [
    'title' => 'Sealify Nigeria API',
],

'security_strategy' => \Dedoc\Scramble\SecurityDocumentation\MiddlewareAuthSecurityStrategy::class,
```

Then generate the OpenAPI spec:

```bash
php artisan scramble:export
cp api.json public/api.json
```

**When to regenerate:** every time you add/change an endpoint:

```bash
php artisan scramble:export && cp api.json public/api.json
```

Or use the shortcut alias:

```bash
# add to ~/.bashrc
alias sealify-docs='cd /path/to/sealify-backend && php artisan scramble:export && cp api.json public/api.json && echo "Docs refreshed"'
```

### 5.5 Run the API

```bash
php artisan serve
```

Listens on `http://127.0.0.1:8000`. Leave this terminal running.

**To bind to a different host (test on phone, etc.):**

```bash
php artisan serve --host=0.0.0.0 --port=8000
```

Then use your laptop's LAN IP (e.g. `http://192.168.1.5:8000`).

## 7. Database Schema

### Identity & Auth

| Table | Purpose |
|---|---|
| `users` | Main user records (name, email, phone, password, status, balance, kyc_verified_at, is_verified_seller, has_used_free_promotion) |
| `password_reset_tokens` | Laravel password reset tokens (unused — we use OTP) |
| `personal_access_tokens` | Sanctum bearer tokens |

| Table | Purpose |
|---|---|
| `categories` | Parent + child categories (self-referential) |
| `listings` | Advertisements |
| `listing_images` | Images per listing |
| `favorites` | User → listing saved ads |
| `promotions` | Active/expired/cancelled boosts |

### Messaging

| Table | Purpose |
|---|---|
| `conversations` | Chat threads |
| `conversation_participants` | Users in a conversation + last_read_at |
| `messages` | Message body, sender, type, conversation_id |
| `message_attachments` | Files (images, voice notes, docs) per message |

### Financial

| Table | Purpose |
|---|---|
| `transactions` | Payment records (all purposes: promotion_boost, future: verification_fee) |
| `bank_accounts` | User payout destinations (with Paystack recipient_code) |
| `withdrawals` | Withdrawal requests with status workflow |
| `wallet_transactions` | Immutable ledger of balance changes (credit/debit/refund) |
| `payment_transactions` | PayZephyr's own audit log (separate from our `transactions`) |
| `webhook_events` | PayZephyr webhook deduplication |

### Trust & Verification

| Table | Purpose |
|---|---|
| `kyc_verifications` | Identity submissions (masked ID, provider response) |

### Admin (Phase 7 — schema ready, endpoints pending)

| Table | Purpose |
|---|---|
| `admins` | Separate admin accounts (role: super_admin/admin/moderator) |

## 9. Authentication Flow

The API uses **Sanctum bearer tokens**. Every protected endpoint requires `Authorization: Bearer <token>`.

### 9.1 Registration (Step 1)

```bash
curl -X POST http://127.0.0.1:8000/api/auth/register \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Test User",
    "username": "testuser",
    "email": "test@example.com",
    "phone": "08012345678",
    "password": "password123",
    "password_confirmation": "password123"
  }'
```

**Response (201):**

```json
{
  "data": {
    "user": {
      "id": 1,
      "name": "Test User",
      "email": "test@example.com",
      "status": "active",
      "email_verified_at": null
    },
    "requires_email_verification": true
  },
  "message": "Registration successful. Check your email for a 6-digit verification code."
}
```

**Important:** No token is issued yet. The user must verify their email.

A 6-digit OTP is sent to the email. It expires in 10 minutes.

### 9.2 Email Verification (Step 2)

```bash
curl -X POST http://127.0.0.1:8000/api/auth/verify-email \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"email": "test@example.com", "code": "123456"}'
```

**Response:** `{"message":"Email verified successfully. You can now log in."}`

**Resend code** (60-second cooldown):

```bash
curl -X POST http://127.0.0.1:8000/api/auth/resend-verification \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"email": "test@example.com"}'
```

### 9.3 Login (Step 3)

```bash
curl -X POST http://127.0.0.1:8000/api/auth/login \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"email": "test@example.com", "password": "password123"}'
```

**Response (200):**

```json
{
  "data": {
    "user": { ...full user object... },
    "token": "1|xxxxxxxxxxxxxxxxxxxx"
  },
  "message": "Login successful."
}
```

**Save the `token`** — every authenticated request needs it:

```bash
TOKEN="1|xxxxxxxxxxxxxxxxxxxx"
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8000/api/auth/me
```

### 9.4 Forgot Password Flow

```bash
# 1. Request reset code
curl -X POST http://127.0.0.1:8000/api/auth/forgot-password \
  -H "Accept: application/json" -H "Content-Type: application/json" \
  -d '{"email":"test@example.com"}'

# 2. Submit new password with the code from email
curl -X POST http://127.0.0.1:8000/api/auth/reset-password \
  -H "Accept: application/json" -H "Content-Type: application/json" \
  -d '{
    "email": "test@example.com",
    "code": "654321",
    "password": "newpassword456",
    "password_confirmation": "newpassword456"
  }'
```

All existing tokens are revoked on password reset.

### 9.5 Logout

```bash
curl -X POST http://127.0.0.1:8000/api/auth/logout \
  -H "Accept: application/json" \
  -H "Authorization: Bearer $TOKEN"
```

Revokes the current token only. Other devices stay logged in.

### 9.6 Session Errors

| Status | Meaning | What to do |
|---|---|---|
| 401 | No token / invalid token / logged out | Re-login |
| 403 | Valid token but email not verified | Complete `/api/auth/verify-email` |
| 403 | Account suspended | Contact support (`account_status: "suspended"`) |
| 403 | Account banned | Contact support (`account_status: "banned"`) |
| 422 | Validation error | Read `errors` object |

### 9.7 Middleware Chain

Each protected route passes through:

1. `api` — global API middleware
2. `auth:sanctum` — checks bearer token
3. `verified` — checks `email_verified_at` (on protected endpoints only)
4. `active` — blocks suspended/banned users immediately

The `active` middleware is what makes suspension take effect instantly — even valid tokens stop working after `UPDATE users SET status='suspended'`.

## 10. API Reference

All endpoints return JSON. Amounts are decimal strings like `"500.00"` (NGN). Timestamps are ISO 8601 UTC.

### 10.1 Public Endpoints (no auth)

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/auth/register` | Create account |
| POST | `/api/auth/login` | Sign in |
| POST | `/api/auth/verify-email` | Verify email with OTP |
| POST | `/api/auth/resend-verification` | Resend OTP (60s cooldown) |
| POST | `/api/auth/forgot-password` | Request password reset |
| POST | `/api/auth/reset-password` | Complete password reset |
| GET | `/api/users/{id}` | Public seller profile |
| GET | `/api/users/{id}/listings` | Seller's active listings |
| GET | `/api/categories` | Full category tree (12 parents + children) |
| GET | `/api/categories/{slug}` | Single category detail |
| GET | `/api/listings` | Browse/search listings (see filters below) |
| GET | `/api/listings/{slug}` | Listing detail (increments views) |

| POST | `/api/payments/webhook` | Paystack webhook (server-to-server) |

**Listings filters** (`GET /api/listings`):

| Query param | Example | Purpose |
|---|---|---|
| `q` | `?q=iphone` | Search title + description |

| `condition` | `?condition=new` | new / like_new / good / fair / needs_repair |

## 11. Payments — PayZephyr (10 Providers)

### 11.1 How It Works

The API uses **[PayZephyr](https://payzephyr.dev)** — a Laravel package that wraps 10 payment providers behind one interface. Your controllers never call Paystack/Flutterwave/Stripe directly; they call `PaymentService`, which calls `Payment::amount()->email()->redirect()`.

This means:

- **Swap providers** by changing one env var (`PAYMENTS_DEFAULT_PROVIDER`)
- **Failover** is automatic — if Paystack fails, Flutterwave handles it (when enabled)
- **Same code** works across all providers
- **Webhook signatures** are handled per-provider by PayZephyr

### 11.2 Supported Providers

| Provider | Country | Env keys required | Enable via |
|---|---|---|---|
| **Paystack** | Nigeria, Ghana, SA | `PAYSTACK_SECRET_KEY`, `PAYSTACK_PUBLIC_KEY` | `PAYSTACK_ENABLED=true` |
| **Flutterwave** | Nigeria, Africa | `FLUTTERWAVE_SECRET_KEY`, `FLUTTERWAVE_PUBLIC_KEY`, `FLUTTERWAVE_WEBHOOK_SECRET` | `FLUTTERWAVE_ENABLED=true` |
| **Monnify** | Nigeria | `MONNIFY_API_KEY`, `MONNIFY_SECRET_KEY`, `MONNIFY_CONTRACT_CODE` | `MONNIFY_ENABLED=true` |
| **Stripe** | Global | `STRIPE_SECRET_KEY`, `STRIPE_PUBLIC_KEY`, `STRIPE_WEBHOOK_SECRET` | `STRIPE_ENABLED=true` |
| **PayPal** | Global | `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_WEBHOOK_ID` | `PAYPAL_ENABLED=true` |
| **Square** | US/UK/CA/AU | `SQUARE_ACCESS_TOKEN`, `SQUARE_LOCATION_ID`, `SQUARE_WEBHOOK_SIGNATURE_KEY` | `SQUARE_ENABLED=true` |
| **OPay** | Nigeria | `OPAY_MERCHANT_ID`, `OPAY_PUBLIC_KEY`, `OPAY_SECRET_KEY` | `OPAY_ENABLED=true` |
| **Paddle** | Global | `PADDLE_API_KEY`, `PADDLE_CLIENT_TOKEN`, `PADDLE_WEBHOOK_SECRET` | `PADDLE_ENABLED=true` |
| **Mollie** | Europe | `MOLLIE_API_KEY`, `MOLLIE_WEBHOOK_SECRET` | `MOLLIE_ENABLED=true` |
| **Razorpay** | India/Global | `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET` | `RAZORPAY_ENABLED=true` |

**Currently only Paystack is enabled** (test mode). Add others by:

1. Getting the required API keys from the provider's dashboard
2. Adding them to `.env`
3. Flipping `<PROVIDER>_ENABLED=true`
4. `php artisan config:clear`

No code changes needed. Failover is configured by `PAYMENTS_FALLBACK_PROVIDER=flutterwave` — so when Flutterwave is enabled, Paystack failures auto-route to it.

### 11.3 Payment Flow

```
┌──────────────────────────────────────────────────────────────┐
│ 1. Frontend: POST /api/payments/initiate                     │
│    Body: { amount: 500, purpose: "promotion_boost",          │
│            metadata: { listing_id: 1, days: 7 } }            │
└─────────────────┬────────────────────────────────────────────┘
                  │
                  ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. API: PaymentService::initiate()                           │
│    - Creates Transaction row (status=pending)                │
│    - Calls PayZephyr Payment::amount()->redirect()           │
│    - Returns: { authorization_url, reference }               │
└─────────────────┬────────────────────────────────────────────┘
                  │
                  ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. Frontend: Redirects user to authorization_url             │
│    (Paystack checkout page — user enters card details)       │
└─────────────────┬────────────────────────────────────────────┘
                  │
                  ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. Provider: Charges card, redirects browser to callback URL │
│    GET /api/payments/callback?reference=XXX                  │
└─────────────────┬────────────────────────────────────────────┘
                  │
                  ▼
┌──────────────────────────────────────────────────────────────┐
│ 5. API: PaymentService::verify(reference)                    │
│    - Calls PayZephyr Payment::verify(reference)              │
│    - If successful: flips transaction → success              │
│    - Fires onSuccess() → creates Promotion row               │
│    - Returns transaction JSON to browser                     │
└──────────────────────────────────────────────────────────────┘
                  │
                  │  (parallel safety net)
                  ▼
┌──────────────────────────────────────────────────────────────┐
│ 6. Provider: Fires webhook POST /api/payments/webhook        │
│    - Verifies signature                                      │
│    - Re-runs verify() (idempotent — safe if step 5 ran)      │
└──────────────────────────────────────────────────────────────┘
```

**Key design choices:**

- **Provider is source of truth.** `verify()` always asks Paystack/Flutterwave/etc, even if local status is "abandoned". This prevents the class of bug where a user pays after our local expiry timer flips to abandoned.
- **Idempotent.** `verify()` can be called any number of times. Both callback and webhook can fire — only one flips the status.
- **Extensible.** `onSuccess()` uses `match ($transaction->purpose)` — adding a new paid feature means one new case, no changes to the payment lifecycle.

### 11.4 Test Cards (Paystack Sandbox)

| Field | Value |
|---|---|
| Card number | `4084 0840 8408 4081` |
| CVV | `408` |
| Expiry | Any future date, e.g. `12/29` |
| PIN | `0000` |

### 11.5 Test Bank Code

Paystack test mode restricts live bank resolves to **3 per day**. Use the test bank code for automated testing:

```
bank_code: "001"
account_number: "0000000000"
```

The endpoint returns `verified: false` for test bank (skips recipient_code creation, which is correct — a test account can't receive payouts).

For real accounts, add with a real Nigerian bank code and real account number — Paystack resolves the name and creates a `recipient_code` for future transfers.

### 11.6 Webhooks

**Our webhook** — `POST /api/payments/webhook`:

- Verifies HMAC signature (per-provider, handled by PayZephyr)
- Deduplicates via `webhook_events` table
- Re-verifies with the provider API (never trusts webhook alone)
- Updates transaction status idempotently

**PayZephyr's webhook** — `POST /payments/webhook`:

- Separate endpoint with its own signature verification
- Logs to `payment_transactions` and `webhook_events`
- Optional (our custom webhook covers everything we need)

For production reliability, point Paystack's dashboard webhook to `https://api.sealify.ng/api/payments/webhook`. That's the one that updates the `transactions` table.

### 11.7 Transaction Statuses

| Status | Meaning |
|---|---|
| `pending` | Awaiting payment |
| `success` | Provider confirmed payment |
| `failed` | Provider rejected (card declined, etc.) |
| `abandoned` | Local expiry passed OR user never paid |
| `refunded` | (future — PayZephyr refund endpoint) |

Note: `abandoned` is **not** terminal — if the user later pays, `verify()` re-checks with provider and flips to `success`. That's the fix from an earlier session.

## 12. KYC Verification — Bytid

### 12.1 Why KYC

Only users with **verified identity** can be **verified sellers** (`is_verified_seller = true`). This drives trust indicators in the marketplace.

Currently, KYC is **optional** — users can still browse, buy, message, and promote without it. When you decide to gate an action (e.g., listing creation, withdrawals), add the `kyc` middleware to that route.

### 12.2 Supported Documents

### 12.5 Bytid Sandbox Test Data

Bytid's sandbox determines result from the **last two digits** of the ID number:

| Last 2 digits | Result | Use case |
|---|---|---|
| `00` | `not_found` | Test rejection path |
| `99` | `failed` | Test provider error |
| `97` | `verified` (second test person) | Alternate success |
| **Any other (e.g., `01`, `11`, `55`)** | `verified` | Standard success |

**Recommended test values:**

- **Success:** `12345678901` (ends in `01`) — resolves to Adaeze Okafor
- **Not found:** `12345678900` (ends in `00`) — no record

### 12.6 Privacy

- **Full ID numbers are never stored.** Only `id_number_last4` and `id_number_hash` (SHA-256).
- **Full Bytid response is logged** in `provider_response` for audit/dispute purposes.
- **Rejected/failed submissions don't update user state** — user can retry with corrected details.

### 12.7 Rate Limiting

Bytid costs money per verification. Our code prevents abuse:

- **60-second cooldown per user** — verified via `pending` status and `created_at` check
- **One active submission at a time** — submitting while pending returns 429
- **Once verified, cannot resubmit** — returns 409

## 14. Withdrawals

### 14.1 Flow

```
User has earnings from sales (or admin credit, for testing)
    │
    ▼
POST /api/auth/withdrawals
    │
    ├─ Checks balance >= amount
    ├─ Checks amount >= WITHDRAWAL_MIN_AMOUNT (₦1,000)
    ├─ Checks bank account has recipient_code (verified for payouts)
    │
    ├─ Deducts amount from balance immediately (hold)
    ├─ Creates Withdrawal (status=pending)
    ├─ Creates WalletTransaction (debit, for ledger)
    │
    ▼
Admin approves (Phase 7 — pending) → triggers Paystack transfer
    │
    ├─ Success: status=completed, provider_transfer_code saved
    ├─ Failure: status=failed, balance refunded
    │
    ▼
Admin rejects → status=rejected, balance refunded
```

### 14.2 Request Withdrawal

```bash
curl -X POST http://127.0.0.1:8000/api/auth/withdrawals \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"amount": 2000, "bank_account_id": 1}'
```

**Response (201):**

```json
{
  "data": {
    "id": 1,
    "amount": "2000.00",
    "fee": "50.00",
    "net_amount": "1950.00",
    "status": "pending",
    "reference": "WDR-XXXXX..."
  },
  "message": "Withdrawal request submitted. It will be reviewed shortly."
}
```

**Balance is deducted immediately** — ₦2,000 held, ₦1,950 payable (₦50 fee).

### 14.3 List Withdrawals

```bash
curl http://127.0.0.1:8000/api/auth/withdrawals \
  -H "Accept: application/json" \
  -H "Authorization: Bearer $TOKEN"
```

Returns all withdrawals with status: `pending`, `approved`, `processing`, `completed`, `rejected`, `failed`.

### 14.4 Business Rules

| Rule | Behavior |
|---|---|
| Minimum amount | `WITHDRAWAL_MIN_AMOUNT` env (default ₦1,000) |
| Fee | `WITHDRAWAL_FEE` env (default ₦50) |
| Payout destination | Must be a bank account with `recipient_code` |
| Balance check | Immediate — insufficient balance returns 422 |
| Ownership | Can only withdraw to own bank accounts |

## 16. Troubleshooting

### 16.1 API doesn't start

```bash
# Check PHP version
php -v     # must be 8.2+

# Check port 8000 is free
sudo lsof -i :8000

# Try a different port
php artisan serve --port=8001
```

### 16.2 500 errors on any endpoint

```bash
# See the actual error
tail -50 storage/logs/laravel.log

# Clear all caches
php artisan optimize:clear
php artisan config:clear
php artisan route:clear
```

### 16.3 "Call to undefined method" errors

Likely a controller method is missing or the file has the empty artisan skeleton. Check the file contains the actual method:

```bash
grep "function " app/Http/Controllers/Api/YourController.php
```

If empty, paste the code from this README or from a previous session.

### 16.4 Database errors

```bash
# Check DB connection
mysql -u root -p -e "SELECT 1;"

# Check tables exist
php artisan migrate:status

# Re-run migrations
php artisan migrate
```

### 16.5 Image URLs return 404

```bash
# Confirm symlink exists
ls -la public/ | grep storage

# If missing, recreate
php artisan storage:link
```

### 16.6 Stoplight "Try it out" hits wrong URL

If the server URLs in `config/scramble.php` don't include `/api`, requests go to `http://127.0.0.1:8000/auth/me` (wrong) instead of `http://127.0.0.1:8000/api/auth/me` (correct).

Fix in `config/scramble.php`:

```php
'servers' => [
    'Local'      => 'http://127.0.0.1:8000/api',
    'Production' => 'https://api.sealify.ng/api',
],
```

Then `php artisan config:clear && php artisan scramble:export && cp api.json public/api.json`.

### 16.7 Payment stuck on "pending"

This is normal if the user hasn't completed payment in the browser. Two options:

- **Browser flow**: user completes payment, callback fires, status flips
- **Manual verify**: `GET /api/payments/verify/{reference}` from any authenticated session

If Paystack confirms payment but our status is stale, `verify` will fix it — it always asks the provider.

### 16.8 Webhook not firing locally

Paystack can't reach `localhost:8000`. Options:

- **Use ngrok**: `ngrok http 8000` → set the ngrok URL as webhook in Paystack dashboard
- **Skip webhook entirely**: our callback path is the primary flow. Webhooks are a reliability safety net, not required for the happy path.

### 16.9 KYC returns 503 "Provider unavailable"

Your `BYTID_API_KEY` isn't set or is invalid. Check:

```bash
grep BYTID .env
```

If missing or wrong, get a new sandbox key from https://www.bytid.com/dashboard, update `.env`, then:

```bash
php artisan config:clear
# restart php artisan serve
```

### 16.10 Composer install fails

```bash
# Check PHP extensions
php -m | grep -E "mbstring|xml|curl|zip|bcmath|mysql"

# If any missing, install:
sudo apt install php-mbstring php-xml php-curl php-zip php-bcmath php-mysql
```

### 16.11 Scramble warnings

You'll see these warnings on `php artisan scramble:export` — they're **cosmetic**, not errors:

- `UpdateProfileRequest` / `StoreConversationRequest`: reference `$this->user()->id` in validation rules. Scramble can't evaluate without an authenticated user. Rules still work at runtime. Safe to ignore.
- `PublicUserResource` "Cannot infer resource model": fixed by adding `@mixin User` docblock (already applied in the current code).

The spec is fully valid — the warnings just mean some field types are inferred loosely, not that they're missing.

- Bytid charges per verification — set a **budget alert** in their dashboard

### 17.4 Storage

Move from local disk to **S3** or **Cloudflare R2**:

```env
FILESYSTEM_DISK=s3
AWS_ACCESS_KEY_ID=...
AWS_SECRET_ACCESS_KEY=...
AWS_BUCKET=sealify-uploads
AWS_DEFAULT_REGION=eu-west-1
```

Then update `config/filesystems.php` disks. Images served from `https://cdn.sealify.ng/...`.

### 17.5 Queue

Run a worker for background jobs:

```bash
php artisan queue:work --queue=default --tries=3 --timeout=120
```

Use `supervisor` or `systemd` to keep it alive.
